# 11. Keeping the pipe small

This chapter covers how to afford fifty players or three thousand entities on a wire that charges by the byte.

The previous chapter covered correct replication. This one covers making it cheap. The tools here are optimizations with sharp edges: each one saves bandwidth by making some failure mode harder to see and each block's docs measure that trade-off.

## Measure first

In [horde_playground](../../examples/horde_playground/), with 128 players and 3000 enemies, the enemies were 9% of traffic and player-to-player broadcast, which is quadratic in players, was 81%. The bytes went on what was sent most often rather than on what looked expensive. `RateMeter::share_of` reports one stream's share of the whole, so that split is a number on the panel. The crate docs ask that a claim about bandwidth be a number on screen rather than a statement in a README. Put the meter up before you optimize anything.

## Relevance

The [`relevance`](../../server_utils/API_REFERENCE.md) module sends each client only what is near it. Morton keys and a `GridQuantizer` map world positions to cells, a `SpatialGrid` answers range queries without scanning the world and a `VisibilitySet` holds each client's visible set as a bitset and diffs it word-at-a-time into exactly the entered/left stream your spawn and despawn messages need. `DenseGrid` is the same surface for a world with known bounds, with its cells in a flat table instead of a hash map; measure before swapping, since on a sparsely filled world the hashed grid is faster. Cell size, the relevance rule and the wire encoding are up to you.

`TierBoundary` needs more care. Any threshold that affects the wire will flap when an entity loiters at the edge, so the boundary is two radii and it takes less distance to stay in than to get in. That hysteresis stops a loiterer from costing a spawn-despawn pair per tick.

## Deltas

Deltas send only what changed. Diffing against what you last *sent* assumes every packet arrives; after one drop the client is permanently missing something that is never mentioned again. [`DeltaBaseline`](../../server_utils/API_REFERENCE.md) diffs against what the client *acknowledged*. The ack is the newest contiguous state rather than the newest bit seen, because the newest bit gives the diff a state that never existed. When measured, that mistake gave recovery statistically indistinguishable from no recovery.

The client half is `DeltaMirror` in the client crate, which shares its types and its one implementation with the server because two separate implementations that agree today will eventually disagree. At 25% simulated loss in horde, the naive diff left 185 unremovable corpses on screen; the acked baseline left single digits, for about 3x the bandwidth of naive. The digest that checks both ends still agree is also the whole resync protocol: dropping the mirror is the resync request and there is no resync message.

On a reliable stream you can skip the acknowledgements. [`Told`](../../server_utils/API_REFERENCE.md) keeps what each viewer was last told and diffs it against what is in their view now, so an unchanging world sends nothing. It needs a stable value to diff against, because a value that jitters is sent every tick.

## Aggregation

Relevance is binary: an entity is in or out. The [`aggregate`](../../server_utils/API_REFERENCE.md) docs say when that is wrong. It works for entities a client only *draws* and fails for entities it has to *compute* with, because dropping an input silently changes the answer. [blackhole_playground](../../examples/blackhole_playground/) is the hard case: clients integrate 2000 pellets through a gravity field and culling distant attractors cut bandwidth while multiplying simulation error 2.4x, because a hole the client was not told about still pulls on every pellet it holds.

`AggregateTree` is Barnes-Hut for the wire: distant groups collapse to one stand-in at their weighted centroid, so their contribution is kept at lower resolution. A single `theta` tunes it and `theta = 0` returns every point exactly, so aggregation off runs the same code path. How coarse you can go depends on the consumer: the gravity field tops out near theta 1.0 and a crowd you only draw is fine at 1.5.

## Deriving instead of sending

[curtain_fire](../../examples/curtain_fire/) runs its enemy bullet curtain as a closed-form function of the tick, derived on every client for free, while player fire is streamed and costs bandwidth for as long as it exists. Its README prices the two against each other on one wire. Before you compress a stream, ask whether it needs to be a stream at all.

## Priority, volumes and subscriptions

Relevance and aggregation both decide *what* to send. How much to send is a separate block: [`priority`](../../server_utils/API_REFERENCE.md) keeps a score per entity that **carries over the ticks it is not sent on**, so the entities that did not fit go next and nothing starves. The budget becomes a ceiling you set rather than whatever the frame happened to cost. [`rest`](../../server_utils/API_REFERENCE.md) is its cheapest input: in a settled scene most things are not moving and saying so costs one bit against the thirty-three a velocity costs. A solver already knows which and `!body.is_sleeping()` is the obvious signal, but check its granularity first: rapier sleeps an **island**, meaning every body in a chain of contacts, so one cube still jostling in a heap reports the whole heap awake. Feeding `rest` a per-body "has this moved recently" instead took cube_yard from 205 cubes claiming to be awake to 56, against 57 that had actually moved.

[spacemo](../../examples/spacemo/) shows a limit of `SpatialGrid` itself; read it before you use a grid in three dimensions. `SpatialGrid` indexes two axes, which is right for a yard or an arena and right for most 3D games, since a landscape is locally 2.5D and a flat grid plus a height check is what shipping MMOs use. In open volume it gets expensive in an unexpected way: a grid on `(x, z)` returns the **disc**, a superset of the sphere, so nobody is ever missed and a lot is over-sent. It measured **7.1x the bandwidth** per client while the game looked entirely correct. The fix is a height filter on what the query returned, which is exact at the same query cost. A volumetric grid sends exactly what the filter sends, so it only helps if it makes the query cheaper. The `field` module in the server crate has all three as `Strategy::Flat`, `FlatBand` and `Volume`, with a `Query` that reports what each one examined, so comparing them means changing one enum. In the control run at slab thickness the flat grid costs 1.00x.

[gow_3d](../../examples/gow_3d/) is where the height filter stops being enough. It is the one place in this tree where one example revised another example's finding. The filter is free when things are spread out, which is what spacemo measured. When things stack it is not: with thirty people on each of twenty-four floors sharing one footprint, the filter is still **exact** but examines **2.7x** what a volumetric grid does, because a flat cell holds every floor at once and 72% of what it pulls out is thrown away. The same people on one floor bring the two back level at 1.00x, which shows the cost comes from geometry rather than crowding. So filter on height when things are spread out and index the third axis when they stack. This only comes up when a tower is taller than the view radius: at eight floors against a thirty metre view the volumetric grid excludes nothing either.

gow_3d is also why this chapter has a second relevance block. Relevance normally means distance, but an MMO also asks who you have *chosen* to follow, wherever they are. Party health bars update across a zone, raid frames work through a wall and a guild roster has nothing to do with distance. The two also have different shapes, so neither can express the other: a grid query is a fresh answer every tick over a set that changes constantly, while a party is five entries that last an hour. Expressing a party as a relevance radius needs an infinite radius; expressing a grid query as a subscription means resubscribing everybody every tick. The block that came out of it is [`subscription`](../../server_utils/API_REFERENCE.md). `Subscriptions<K>` is indexed **both ways round** because both directions are needed every tick (a sender needs the set to include and a departing key needs everyone who has to be told, which costs a scan of every subscriber in the world if you only keep one). `Audience::of` unions it with a grid answer. The union keeps the second channel cheap: `Audience::added` counts only the members distance missed, so it is zero for the people standing beside you. The frame also has to say **why** each entity is in it, because "near" and "subscribed" behave differently: the neighbour vanishes when you walk away and the party member does not. A client that cannot tell them apart cannot draw the interface the subscription exists for.

Three more examples use the same block in different ways. [horde_playground](../../examples/horde_playground/) already handled "where is everybody" with a **far tier**: every player, quantised to two bytes, on a slow clock. That is really a broadcast and it costs the whole arena on every frame it is due, so a squad subscription stays flat at 39 bytes where the far tier reaches 396 at 128 players. Below about eight players the broadcast is cheaper, so a channel that is right at scale can be wrong at the size you are testing at. [spacemo](../../examples/spacemo/) uses it at the other extreme, **one entry held for seconds**: a missile lock at 320 units against a 260 view could name a ship relevance had already culled, so the reticle pointed at something the client was never sent. Fixing it raised an earlier question, since a lock re-derived from the cone every tick is really a spatial query and nothing can subscribe to a set that changes that fast.

[fog_skirmish](../../examples/fog_skirmish/) does not use it. A subscription tells a client about something it cannot see and in a fog-of-war game that is a cheat. The only entities a player may know about at any distance are their own units and ownership already covers that without a subscription set.

Before reaching for any of this chapter's blocks, ask which of what you send the receiver could have worked out. spacemo has two projectiles that differ by one field: a straight shot and a homing one. Streaming every path carries 17.3x the shots per frame of sending the straight shot as a spawn and streaming only the homing one. Compression makes a path cheaper, but a path the receiver can derive does not need to be sent at all. That only works when nothing can change the path after the packet leaves; the homing shot is the case where something can.

spacemo also shows the cost this chapter's blocks are least likely to catch. Priority, rest and delta all keep a standing world **fresh**. Entities that come and go cost bytes at entry and exit instead and in a firefight they dominate: with every path streamed, 83.0 bolts cost 1091.2 bytes a frame against 133.0 for 8.0 ships, so the bolts cost eight times what the ships do.

[cube_yard](../../examples/cube_yard/) measures all of this end to end. 901 cubes went from 23.90 Mbit/sec to 4.20 by quantising and bit packing, but encoding alone has a floor it cannot get past. The priority budget took it to **0.23**, so the last 16x came from choosing what to send rather than from compressing it. Two lessons from the example: budget the *wire* including the envelope or you overshoot by the frame around the payload. Prefer `order`/`sent` over `fill` when a cube's real cost spans an order of magnitude, since packing until full beats any estimate generous enough to be safe.

You can use any of these blocks without the others: a grid without deltas, deltas without aggregation or your own interest rule over the same bitset diff. The blocks share only small vocabulary types (slot keys, digests) that live in the client crate so a browser can run its half. Every block also exposes its error counters, with phantom counts beside missing counts. A starved mirror holds nothing wrong, so a count of wrong entries present needs a count of correct entries missing beside it.

## The lab

[horde_playground](../../examples/horde_playground/) with the HUD meters up: watch share_of show where the bytes go, then add loss with the sliders and watch the acked baseline recover where naive recovery would fall apart. Then [blackhole_playground](../../examples/blackhole_playground/) to see aggregation as a correctness setting, including a negative result: correcting the worst-off pellets first loses to a plain round-robin sweep by 2.4x to 3.5x, because a bounded sweep is what actually bounds error.
