# 40. The right to say no

This chapter covers how to refuse, limit and end connections (kick, ban, time out, expire, drain) without the library deciding any of those policies for you.

If you are building an app rather than a game, this chapter matters even more to you: moderation, rate limiting, session expiry and graceful deploys are everyday work in collaborative tools and everything below applies to both.

## Mechanism and policy

In plaza the mechanism lives in the layer that sees the traffic and the policy lives above it, with no exceptions. The session can refuse a socket, resolve an agent to its connections, close a connection with a farewell, read per-connection activity and volume and enforce a deadline. The session never knows *why*: ban lists, thresholds, timeouts and which duplicate login wins are up to you. Where a default would decide policy for everyone, plaza ships none. There is deliberately no `kick_after` option anywhere in plaza.

On the game side, a forced disconnect looks exactly like a cable pull. Every departure arrives as the same `Left` event, so your logic has one disconnect path and what a removal *means* (seat cleared versus seat held, [chapter 12](12-players-come-and-go.md)) is recorded in your state rather than in a second set of presence events.

## The mechanisms, in the order a connection meets them

**Admission.** A connection can be refused before anything is created. When the route can tell who is connecting before the upgrade, it decides there: on WebSockets your HTTP route answers with an error, on TCP the `AgentFactory` returns `Err(Farewell)` and the socket hears one `Goodbye` and nothing else. A browser or mobile client cannot set a header on its upgrade, so for it the transport takes a `ConnectionAdmitter` (`admit_connection` on WebSockets, `bind_with_admitter` on TCP). The socket waits on its own task, unregistered, until the client sends a `Kind::Credential` frame after its `Hello`. The admitter then answers `Admitted(agent)` or `Refused(farewell)`. A refusal registers nothing and announces nothing, so a ban, a capacity rule, a per-address cap and a duplicate login are all judged at the door without a registration to undo. A data frame sent before the credential closes the socket with 4401, a socket that presents nothing within `Limits::credential_timeout` (5 seconds by default) is closed with 4408 and `Limits::pending_connections` caps how many may wait at once. The admitter cannot read the authoritative state, because the controller has not heard of the connection yet; a rule that needs game state goes in an `OpGuard`, which the controller runs on each op before your rules see it.

**Resolution.** A decoded op names an agent, but acting on it needs a connection. `connections_of` maps one to the other and presence events carry the connection id, so removing an account always gives you a handle to act on, even when the account holds two sockets.

**The close.** `close_connection` flushes what was queued, writes a `Goodbye` frame carrying your `Farewell` *last*, then closes the socket. A `Farewell` is a close code plus optional detail bytes the session never reads. Codes 4000 to 4999 are yours, so "removed by the host" and "away from the table" are two codes with your own wording in the detail. On WebSocket the close frame repeats the code and on TCP the `Goodbye` is the only place it travels. A `plaza_ws` client reads it as `Arrival::Closed`, whose `refused()` is true for a 4xxx code. `deregister_agent` closes every connection an account holds; `disconnect_all` drains the room through the same path, telling each connection and then closing it, so a graceful shutdown is a kick applied to everyone.

**The readers.** `idle_for` reports how long a connection has been silent. Only the session can answer that correctly, because the session answers latency probes without your code seeing them; an AFK rule written above the session either counts probe traffic as activity or never fires. `connection_inbound` counts frames and bytes per connection, which the session-wide stats cannot break down; your threshold plus that counter makes a flood rule. Both only report values and neither runs a timer: you check them from your own loop against your own numbers.

**Inbound rate limiting.** A flood is the one rule you cannot enforce by checking a reader from your loop. By the time your loop looks, the flood has already filled the queue every connection shares and the frames it cost belonged to other players. So `rate_limit_inbound` sets a `Rate` that the session enforces on the connection's own task, with one bucket per connection, before anything shared is touched. A client over the rate is refused without anyone else paying for it. The numbers and the response are yours. `Over::Shed` drops the frame and keeps the connection and `Over::Close` ends it with 1008 Policy Violation. Which one a rate needs depends on your own protocol. The rate is an **accruing budget** rather than a window, the same conclusion the validator below reaches from the other direction. `TransportStats::inbound_shed` is the refusal count for the session and `connection_inbound` reports `shed` per connection; the validator section below treats that count as the whole defence.

**The deadline.** `set_deadline` limits how long a session lasts and the connection's own task enforces it; setting it again renews it. An arcade credit, a trial period and an auth token expiry all use this one mechanism with different policies.

## Policy worked examples

Both labs are built from the library's blocks with no transport of their own:

- [door_policy](../../examples/door_policy/) is admission and identity: a per-address cap, a ban, a capacity rule and both duplicate-login policies (refuse the newcomer, kick the older) all judged in one `ConnectionAdmitter` before the connection registers, plus a credit that buys minutes through `set_deadline`. Kicking the older login works because the loser is registered and the newcomer is not yet. Which login loses is your choice.
- [table_manners](../../examples/table_manners/) is moderation at a table: kicks that give a reason, AFK removal that probe traffic cannot postpone, a flood shed at the door and a flooder removed only if it keeps pushing (neither costing a bystander a frame), a drain that tells everyone before closing them and the kick-versus-drop seat handling from [chapter 12](12-players-come-and-go.md), with every claim asserted as a count.

The examples also cover server authority beyond removing players: [auction_floor](../../examples/auction_floor/) arbitrates contested claims with a floor built from what the server measured rather than what the client said and [ghost_trials](../../examples/ghost_trials/) checks a lap time by replaying the claimant's own inputs, so its anti-cheat is a single equality check. Governance covers every place the server's word outranks a client's, which includes more than ending sessions.

In [gow_3d](../../examples/gow_3d/) the server's word is deliberately *weaker* than a client's. It is covered here rather than in a netcode chapter because giving up that authority is a governance decision. The client owns its own position and the server only sanity-checks it. That gives perfectly smooth local movement with nothing to reconcile, at the cost of a class of cheating that can only be limited and never closed. The limit is a sharp cutoff rather than a gradual one: a 1.3x speed cheat works at exactly 1.3x and a 2.0x one achieves 0.13x of an honest run. Nothing separates the 1.3x cheat from a late packet, because the server sees the same thing in both cases. A threshold tight enough to catch it throws out honest players on bad connections.

The lessons from writing that validator apply well outside games.

**Per-request credit.** Measuring each claim against the time since the last one wrongly refuses requests that bunch up, since two arriving in the same millisecond measure zero elapsed against each other. The obvious fix, crediting a minimum interval per request, opened a hole twice as bad as the one it closed. Whatever you credit per request is a rate the caller can claim at will, so per-request credit multiplies the allowed rate: a client sending twice per tick got a full tick each time and a 2.0x cheat passed at a full 2.00x. What works is an **accruing budget** spent by the action, because it accrues from the clock however many times it is asked. Rate limits, token refills and quota accounting use the same design for the same reason.

**Counting refusals.** A refusal does not stop a cheater but it does record them. The budget must be capped or a disconnection becomes a teleport and even capped, a client that keeps sending an impossible claim eventually banks enough to land one. Over twenty seconds of doing exactly that it gained **180 units against the 187 an honest runner covers, with 591 refusals logged.** The cheat ends up behind and is logged the whole way. Counting refusals is therefore the whole defence. The count reads zero for every honest client, so put it on a panel.

**Derived terrain.** gow_3d's ground is a rule both ends compute from one seed rather than a payload anyone sends. That was done to save bytes, but it also lets the server refuse a claim more than a jump's apex above the ground. A speed budget never sees a client hovering, because hovering costs no horizontal distance at all, so the height rule catches a whole class of cheat the speed budget misses. Anything the two ends derive rather than exchange is available to a validator for free, which is a reason to derive it beyond the bandwidth saving.

**Measuring the right quantity.** A budget that spends 3D distance charges a player walking uphill for the climb and refuses them for going up a slope. A run speed is a speed over the ground; vertical movement is for the height rule to check. A budget must measure only the quantity it limits. One that also includes a second quantity refuses honest callers on exactly the terrain the feature was built for.

**Server-initiated moves.** Under client authority nearly every position travels from client to server. A respawn is the exception: the server puts the character somewhere new and the client, which owns where it stands, has no way to work that out. If it is told nothing, it stays where it died and every claim it sends afterwards is outside the budget from its new position, so it is refused for the rest of the session. The move needs its own idempotent channel, using a **counter rather than a flag**. The move must be applied exactly once: a flag that stays set fights every step afterwards and one that clears itself is lost with a dropped frame. The client compares the counter against the last one it acted on, so a missed frame is caught by the next. This is the same reasoning as an idempotency key on a request that must not be replayed.

## Replacing it

There is nothing to replace: this API is already blocks, so the assembled policies stay in application code. The two example READMEs are the recipes and they also record what they could not simplify. A rule that judges ops rather than connections has its own seam: an `OpGuard` set with `StateControllerBuilder::guard` runs on each op before `process_input` and a refused op never reaches the rules.
