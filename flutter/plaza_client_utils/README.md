# `plaza_client_utils` (Dart)

**License:** Mozilla Public License 2.0 (MPL-2.0) · **Status:** Experimental

Real-time client primitives: prediction and reconciliation, interpolation and extrapolation, rollback, the estimators that size a buffer, and the bookkeeping a delta stream needs. Pure Dart with no dependencies, and nothing in it knows about a transport.

The Rust crate of the same name stays authoritative. Every module here carries its Rust unit tests transliterated, and `flutter/fixtures/` holds behaviour vectors generated by Rust so a later change on that side fails a test here.

Full surface in [API_REFERENCE.md](API_REFERENCE.md).

## Install

```yaml
dependencies:
  plaza_client_utils:
    path: ../plaza_client_utils
```

```dart
import 'package:plaza_client_utils/plaza_client_utils.dart';
```

[`plaza_flame`](../plaza_flame/) re-exports all of it. The deterministic network simulator is a **separate entry point**, `package:plaza_client_utils/net_sim.dart`, matching the Rust crate's `net-sim` feature gate: it is a test and demo aid, and an app should not pull it in by accident.

## Four principles worth knowing before you predict or render anything

None is enforceable by a type, and between them they account for every netcode bug found building the Rust playgrounds. They **prevent** bugs; everything else here only recovers from them.

**A shared rule must be shared code, not code written twice.** The `apply` you hand a predictor is meant to *be* the server's step function, not a client approximation of it. Anything the server does that your copy leaves out arrives as a permanent correction: it looks like network jitter, it is largest exactly when it is most visible, and it is expensive to find later. If your rule needs the world to run (gravity, wind, a moving platform), that is what the context parameter is for.

**Prediction is presentation; shared rules consume authoritative state.** Feeding a locally predicted position into a rule *both* sides run creates a second, divergent world, and every packet then fights the local one. Prediction drives the camera and the local player's own marker; the rules both sides run read the authoritative state, even though it is older.

**One instant per frame.** A client that renders in the past picks a single instant T for the whole frame, and everything is evaluated at T: not only where entities are drawn, but everything a behaviour rule reads while producing the frame, aim targets included. [`InterpolationClock`](API_REFERENCE.md#class-interpolationclock) supplies T; feeding every read from it is your discipline.

**The timeline comes from declaration, not arrival.** Round trips and jitter may size buffers. They never decide which moment is on screen or when an input executes; those are numbers the server chooses and publishes. A render clock steered by packet arrival hides bad links instead of reporting them, and quietly makes ping an input to the game.

## Which predictor

The two local-player bundles differ by how the **server** consumes input, not by how the client feels. Choosing wrong is silent, and shows up as a prediction that is always slightly behind.

| the server | use |
|---|---|
| consumes one input per simulation step | [`PredictedPlayer`](API_REFERENCE.md#class-predictedplayer) (replay unacknowledged inputs) |
| holds an input and integrates it every tick | [`HeldInputPredictor`](API_REFERENCE.md#class-heldinputpredictor) (dead reckon and ease) |

Replaying inputs against a server of the second kind double counts, and gets worse the more you economise on bandwidth, because one coalesced input can cover a long stretch of simulation. [`InputCoalescer`](API_REFERENCE.md#class-inputcoalescer) therefore pairs with the second and **not** the first, where dropping repeats drops actual movement.

`HeldInputPredictor` is not only for the entity you control. It runs a rule locally and corrects from sparse authoritative samples, and nothing in it cares whether the held input came from a keyboard. For an entity whose behaviour you know, hold its *intent* (an enemy's target, a vehicle's waypoint), put the world it reads in the context, and it becomes a locally simulated remote.

## Drawing an entity you do not control

Four options, and the choice is a property of **the entity**, not of the game. Different entities in one scene legitimately sit on different rows. Take the highest row you have the data for.

| you know | draw it by | piece |
|---|---|---|
| its rule, and the inputs the rule reads | running that rule locally, corrected by samples | [`HeldInputPredictor`](API_REFERENCE.md#class-heldinputpredictor) |
| nothing but its past positions | interpolating between two real samples, in the past | [`RemoteView`](API_REFERENCE.md#class-remoteview), `interpolate: true` |
| its positions, and that its motion is constrained | dead reckoning along the last velocity, briefly | `RemoteView`, `extrapolate: true` |
| none of the above | holding the newest sample | `RemoteView`, both off |

Measured over 3000 enemies in the Rust `horde_playground`, running the rule beats interpolating by 43 px of mean error at 1 Hz and still leads at 30 Hz, because an interpolated entity is always a send interval in the past.

The bottom rows are not interchangeable either. Dead reckoning a **player** is guessing at a human's intention, which nothing on the wire carries, so it overshoots every direction change. It is for entities with inertia and a turning limit.

## The prediction loop

1. The player acts. Apply it locally at once and record it with its sequence number, so the screen responds without waiting for a round trip.
2. The server eventually replies with authoritative state plus the last sequence number it processed.
3. Acknowledge everything up to that number, snap to the authoritative state, then **replay** the inputs it had not yet seen. The result is the server's truth plus your still-pending actions.

A misprediction corrects itself on the next reconciliation. That is the design, not a failure.

```dart
final player = PredictedPlayer<Pos, Move, World>(
  initial: spawn,
  apply: stepPlayer,          // the same rule the server runs
  lerp: (a, b, t) => a.lerp(b, t),
  context: world,
);

// on input
final seq = player.input(move);
client.sendOp(variant('Move', {'seq': seq, 'dx': move.dx, 'dy': move.dy}));

// on the server's reply
player.reconcile(authoritative, ackedSeq);

// every frame
player.advance(dt);
draw(player.render());       // eased, for the eye
resolveRules(player.logical); // exact, for the game
```

`logical` and `render` are separate on purpose: game rules must not read a state that has been smoothed for the eye.

## The resume contract

Every long-lived client eventually stops reading: an app is backgrounded, a laptop sleeps, a frame loop stalls. The socket keeps receiving the whole time, so what a resumed client faces is not a slow stream but a *lump*: minutes of packets, delivered at once, describing moments it can never play.

One invariant makes the recovery work: **a client may discard any stretch of the stream unread, provided it also drops the state derived from it**, because an acknowledgement carrying the digest of nothing obligates the server to answer with a full baseline. That is why there is no resync request message anywhere. Dropping the mirror *is* the request.

Your remaining job is small and cannot be taken from you: on [`Admission.timelineLost`](API_REFERENCE.md#enum-admission), drop the [`DeltaMirror`](API_REFERENCE.md#class-deltamirror) and re-anchor the render clock on what just arrived. [`plaza_flame`](../plaza_flame/) does the transport half for you.

## Rollback, the other family

[`RollbackSession`](API_REFERENCE.md#class-rollbacksession) is the peer-to-peer deterministic model, not the server-authoritative one: each peer predicts every other peer's input, and rolls back and re-simulates when a confirmation disproves a guess.

It needs a **deterministic** step (same state and inputs in, same state out, on every peer) and an input type with a meaningful `==`, because that comparison is how a confirmation is judged against the guess it replaces. A type with identity equality reports every confirmation as a misprediction.

## Two Dart-specific rules

**Rules are functions, not traits.** Where the Rust crate constrains a type with `Interpolatable` or `Extrapolatable`, this takes a `lerp` or `extrapolateBy` function. Same information, no trait system to lean on.

**`Frame` is not exported from the barrel.** The Rust crate re-exports `rollback::Frame`, an alias for a frame index. This does not, because [`plaza_wire`](../plaza_wire/) exports a `Frame` class for a wire frame and an app importing both could name neither. A frame index is an `int`; the alias is still in `src/rollback.dart` for anyone who wants it by direct import.

## The counters that stand in for Rust's warnings

The Rust crate logs `tracing::warn!` at four points. A Dart library has no logger to reach for, so each is a counter instead, which is more useful anyway because a non-zero value is a fact rather than a line that scrolled past:

| Counter | Non-zero means |
|---|---|
| [`ClientInputBuffer.overflowed`](API_REFERENCE.md#property-overflowed) | Replay is already incomplete: inputs were dropped before the server acknowledged them. |
| [`StateHistory.resets`](API_REFERENCE.md#property-resets) | Frames were saved non-contiguously, which rollback assumes never happens. |
| [`ExtrapolationBase.overExtrapolations`](API_REFERENCE.md#property-overextrapolations) | Steadily: the render target is computed the wrong way and sits ahead of the newest sample, so nothing ever interpolates. |
| [`RemoteView.overExtrapolations`](API_REFERENCE.md#property-overextrapolations-1) | This entity's packets have stopped arriving and the view is drawing a guess that has stopped improving. |
